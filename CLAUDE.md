# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A Super Nintendo (SNES) homebrew platformer written in C, built with **PVSnesLib** (a C SDK for the SNES built on the `tcc816` compiler and the `wla-65816`/`wlalink` toolchain). Target platform: LoROM, SlowROM, 8 ROM banks. Output is a `.sfc` ROM run in the **Mesen** emulator.

The vendored SDK and emulator live under `tools/` (`tools/pvsneslib/`, `tools/mesen/Mesen.exe`) and are third-party — do not edit files under `tools/`.

## Environment setup

Build tooling is not on PATH by default. Two ways this is provided:

- **One-time (persistent)**: `powershell -File tools/setup_env.ps1` sets the `PVSNESLIB_HOME` / `DEVKITSNES` user env vars and adds `tools/pvsneslib/devkitsnes/bin` and `C:\msys64\usr\bin` to the user PATH.
- **Per-run (session-local)**: `run.bat` sets `PVSNESLIB_HOME`, `DEVKITSNES`, and `PATH` inline before building — this is what to use if the persistent env vars haven't been set up.

The build requires MSYS2 (`C:\msys64`) for `make` and other POSIX tools, plus the SDK binaries in `tools/pvsneslib/devkitsnes/bin/` (`816-tcc.exe`, `wla-65816.exe`, `wla-spc700.exe`, `wlalink.exe`).

## Common commands

Build and run (from the repo root, in PowerShell or CMD; compiles, then launches the ROM in Mesen). `run.bat` always runs `make clean` first, so every graphic is reconverted and the build is slower than a plain `make`; on a compile error it prints `[ERROR]` and pauses:
```
cd E:\ProyectoSNES
.\run.bat
```

Run the already-built ROM without recompiling (check the `ProyectoSNES.sfc` timestamp first — if code changed since it was built, use `run.bat` instead):
```
& "E:\ProyectoSNES\tools\mesen\Mesen.exe" "E:\ProyectoSNES\ProyectoSNES.sfc"
```

Build only, from an MSYS2 bash shell with `PVSNESLIB_HOME` exported:
```
make
```

Clean build artifacts, ROM, and graphics/audio conversion outputs:
```
make clean
```

Build only, from PowerShell (what Claude Code should use — the sandboxed Git Bash tool cannot run `wla-65816`, which writes a temp file to the drive root):
```
$env:PVSNESLIB_HOME="/e/ProyectoSNES/tools/pvsneslib"; $env:PATH="E:\ProyectoSNES\tools\pvsneslib\devkitsnes\bin;C:\msys64\usr\bin;"+$env:PATH; make
```

**`snes_rules` does not track header dependencies**: editing a `.h` (or a `#define` used by several files) does not recompile the `.c` files that include it. After any header change run `make clean` before `make`, or stale objects keep the old values silently (this bit us once with fade timings). Assets are embedded by `data.asm` via `.incbin`; the Makefile declares `data.obj: $(ASSETS)` so a regenerated image reassembles it (without that line, old graphics stayed in the ROM).

The equivalent VS Code tasks (`.vscode/tasks.json`) run these same `make` invocations through `C:\msys64\usr\bin\bash.exe`: **"Build SNES ROM"** (default build task, `Ctrl+Shift+B`; it only compiles, it does not launch Mesen) and **"Clean Project"**.

What the current ROM does when run: the boot sequence only (Nintendo → publisher → devs → dedication → 3-scene intro → title with parallax). Start on the title goes to "LEVEL 1 - COMING SOON" and Start there returns to the title; 15 s without input on the title loops back to the intro. Gameplay does not exist yet (the design is in `docs/diseno-demo-jugable.md`). Mesen's keyboard-to-pad mapping is configured in Mesen under Options → Input.

There is no test suite or linter in this project.

## Architecture

- `src/main.c` — minimal entry point: `video_texto_mode1()`, hide sprites, `secuencia_iniciar(PANTALLA_NINTENDO)`, then the `while(1){ secuencia_actualizar(); WaitForVBlank(); }` loop. One loop iteration = one frame (60 Hz NTSC).
- `src/secuencia.c/.h` — screen state machine (`enum Pantalla` + `switch`); `frames_en_pantalla` counts frames since the current screen started. Every screen exposes `pantalla_X_iniciar()` (once) and `pantalla_X_actualizar()` (per frame).
- `src/pantallas.h` — screen list, all timings in frames (`SEGUNDOS(n)`), `PERMITE_SALTO`.
- `src/pantalla_*.c` — one file per screen: nintendo, publisher, devs, dedicatoria, intro (3 scenes), titulo, proximamente.
- `src/comun.c/.h` — VRAM layout constants, `video_texto_mode1()`, font loaders (4bpp/2bpp), `fondo16_cargar()`/`fondo256_cargar()`, text helpers (typewriter), fades.
- `src/personajes.c/.h` — the two demo sprites (64x64, 4 frames each = the 512-tile OAM limit), load/show/animate/hide.
- `data.asm` — every graphic asset embedded with `.incbin` in its own `superfree` section (each must fit a 32 KB bank). Labels are referenced from C as `extern char nombre;`.
- `res/` — build inputs per screen (`res/nintendo`, `res/intro`, `res/titulo`, ...), generated by `scripts/componer_escenas.py`, `scripts/generar_fuente_consola.py`, `scripts/preparar_sprites.py` from raw downloads in `res/descargas/` (git-ignored). gfx4snes outputs (`.pic/.pal/.map/.inc/_data.as`) are git-ignored and rebuilt by `make`.
- `docs/diseno-secuencia-arranque.md` — the living spec of the boot sequence (decisions, per-screen technique, verified SDK findings in §10). `docs/glosario-snes.md` — concepts referenced by code comments (`→ glosario: X`). `docs/plan-desarrollo.md` — the learning roadmap (Etapa 1.5 = this demo).
- Every line of game code carries a Spanish comment (project rule: the owner is learning C and SNES from this code).
- `Makefile` — declares `ROMNAME`/`ROMTITLE`, one gfx4snes rule per asset, `bitmaps` and `data.obj: $(ASSETS)`, then includes the SDK's `snes_rules` (`.c` → `.ps` → `.asm` → `.obj` → `.sfc`). `hdr.asm` and `linkfile` are auto-generated; do not hand-edit.
- Build outputs at the repo root (`ProyectoSNES.sfc`, `.sym`, `*.obj`, `ProyectoSNES.log`) are generated artifacts.
